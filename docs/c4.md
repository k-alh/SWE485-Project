# C4 Model

Three views: who uses Talea, what runs, and how the API is composed internally. The
data model follows the component view.

## Level 1 — System context

```
                    ┌──────────────────────────┐
                    │   Student (Year 3–5 or   │
                    │   graduate)              │
                    └───────────┬──────────────┘
                                │ browses, saves, moves applications
                                ▼
   ┌──────────────────┐   ┌──────────────────────────┐   ┌───────────────────┐
   │ Admin / career   │──▶│        TALEA             │◀──│ AI provider       │
   │ services staff   │   │  catalogue + pipeline    │   │ (optional)        │
   └──────────────────┘   └──────────────────────────┘   └───────────────────┘
        pastes text,            stores accounts,
        reviews drafts          listings, applications
```

- The **student** is the reason the system exists; every other element serves them.
- The **admin** is a person, not a service. They paste opportunity text and approve
  drafts. Nothing enters the catalogue without them.
- The **AI provider** is optional and outside the trust boundary. In the default
  configuration it does not exist at all: the mock extractor runs in-process, offline.
  When a real provider is enabled it is treated as untrusted output, and its result is
  only ever a draft.

No other system is called. Talea does not scrape, does not read university systems and
does not talk to company portals.

## Level 2 — Containers

| Container | Technology | Responsibility |
| --- | --- | --- |
| Web client | React 18 + Vite, port 5173 | Five screens, client-side routing, forms, pipeline board |
| API | Fastify 5 on Node 20, port 3000 | Auth, authorisation, validation, all business rules |
| Shared domain | TypeScript package | Pipeline map, deadline status, eligibility, dedupe key, Zod schemas |
| Database | SQLite file via Prisma | Users, sessions, listings, tracker entries, status events, extraction drafts |

```
  Browser
    │  HTTPS / fetch, httpOnly session cookie
    ▼
  ┌──────────────┐   JSON    ┌──────────────┐   Prisma   ┌──────────────┐
  │ Web (Vite)   │──────────▶│ API (Fastify)│───────────▶│ SQLite file  │
  │  :5173       │◀──────────│   :3000      │◀───────────│  dev.db      │
  └──────┬───────┘           └──────┬───────┘            └──────────────┘
         │                          │
         └──── imports ─────────────┘
                    │
             ┌──────▼───────┐
             │ @talea/shared│  rules + types, no I/O
             └──────────────┘
```

The web client imports `@talea/shared` for display (labels, transition buttons, deadline
pills) but never decides anything: every rule it shows is enforced again in the API.

## Level 3 — API components

```
routes/                 services/                    auth.ts
  auth.ts                 extractor.ts (provider)      hashPassword / verifyPassword
   ├ POST   /auth/register  ├ mock provider (offline)   startSession / endSession
   ├ POST   /auth/session   └ openai provider          getCurrentUser
   ├ GET    /auth/session                                requireUser / requireAdmin
   └ DELETE /auth/session  listings.ts
                            ├ parseEligibility
  listings.ts               ├ serializeEligibility
   ├ GET /listings          ├ deadlineToDate
   └ GET /listings/:id      └ toListingDto

  tracker.ts              db.ts                        config.ts
   ├ GET   /tracker         Prisma client singleton     env parsing + defaults
   ├ POST  /tracker
   └ PATCH /tracker/:id   errors.ts
                            AppError, notFound,
  admin.ts                  forbidden, conflict
   ├ POST  /admin/listings
   ├ PATCH /admin/listings/:id
   └ POST  /admin/extractions
```

Request path for a status change, the most rule-heavy operation:

1. `requireUser` resolves the session cookie to a user or throws 401.
2. Zod parses the body; a malformed target status is a 400, not a 500.
3. The entry is loaded with `userId` in the `where` clause, so another student's id is a
   404 rather than a 403.
4. `assertTransition` from `@talea/shared` throws 409 `INVALID_TRANSITION` naming the
   legal targets.
5. Entry update and status event insert run in one Prisma transaction.

## Level 4 — Data model

```
User ──1:N── Session
  │
  └──1:N── TrackerEntry ──1:N── StatusEvent
                  │
                  └──N:1── Listing
                                ▲
AiExtractionDraft ──────────────┘  (draftId links an approved draft to its listing)

Listing         id, title, organisation, type, city, description,
                deadline (date), eligibilityYears (csv), dedupeKey (unique),
                isActive, createdById, timestamps
TrackerEntry    id, userId, listingId, status, note, timestamps
                unique(userId, listingId) — one entry per student per listing
StatusEvent     id, entryId, fromStatus, toStatus, note, createdAt
Session         id, tokenHash, userId, expiresAt
AiExtractionDraft id, rawText, fields (json), missing (json),
                flaggedInstructions (json), provider, createdById, listingId
```

Two constraints carry rules that would otherwise live in code:

- `Listing.dedupeKey` is unique. The database, not a `SELECT` before `INSERT`, decides
  what a duplicate is. A race between two admins ends in a 409 either way.
- `TrackerEntry(userId, listingId)` is unique. Saving twice cannot create two entries,
  even with two clicks in flight.

The status is stored on the entry for fast reads, while `StatusEvent` holds the full
history. They are written in the same transaction, so the two cannot disagree.
